# 代码注释规范

> 本文是 MuseAlgo-OJ 注释的唯一准则。目标不是「注释多」，而是**让第一次读这个仓库的人，不用猜作者为什么这么写**。

## 一条判断标准

写注释前问自己：

> **删掉这行注释，下一个人会不会做出错误的改动？**

会→ 写。不会 → 别写。

一段长篇大论的类注释，如果只复述了类名和方法名，说明它是噪声。宁可没有。

## 分层要求

### L1 必写

| 对象 | 要求 |
|---|---|
| 类 / 接口 | 类头说明**职责 + 边界 + 存在理由**。三选二也要写，但不能只写一句同义反复（如 `/** 用户服务 */`） |
| 非平凡公开方法 | 四要素：**做什么 + 关键参数约束 + 返回语义 + 抛什么异常** |
| SQL 迁移文件 | 文件头说明**这次改了什么业务问题 + 依赖哪几条前序迁移** |

### L2 应写

| 对象 | 要求 |
|---|---|
| 业务关键字段 | 状态机取值、特殊语义标志位、阈值与超时常量——只看名字猜不出含义的才写 |
| 非平凡算法 / SQL | 解释**思路与取舍**，不逐行翻译代码 |

### L3 不写

- Lombok 生成的 getter / setter
- 纯 CRUD 的 Controller 方法（`@Operation` 已说明接口用途，Javadoc 是重复）
- Vue 模板区的 HTML 注释、简单的 CSS 分区
- 自解释的赋值语句（`this.count = count;`）
- 任何「临时注释」和 `TODO`（要做的事请开 Issue）

## 决策型注释：本次的核心

**这是最有价值的注释类型，也是本项目明确鼓励的类型。**

当代码里存在「看起来可以简化，但一简化就错」的地方，必须写清原因。典型场景：

```java
// ✗ 差：读者只能看到做了什么，看不出为什么不能改
@Value("#{${judge0.language-ids:{java:62, c:50, cpp:54, python:71}}}")
private Map<String, Integer> languageIds;
```

```java
// ✓ 好：说明了取值来源、可覆盖性、以及默认值的版本依据
/**
 * Judge0 语言 ID 映射，可通过 {@code judge0.language-ids} 配置覆盖。
 * 默认值对应 Judge0 CE v1.13.0。
 */
@Value("#{${judge0.language-ids:{java:62, c:50, cpp:54, python:71}}}")
private Map<String, Integer> languageIds;
```

再如把HTTP 客户端换掉这种重构，必须留下「为什么换」：

```java
/**
 * Judge0 HTTP 客户端。
 * <p>
 * 由 Hutool HttpRequest（每次新建 TCP 连接）换为 RestClient + JDK HttpClient：
 * JDK HttpClient 内置连接复用（Keep-Alive），判题并发化后不再被握手开销拖慢。
 * 连接超时 10s、读取超时 20s（与原行为一致）。
 * </p>
 */
```

### 本项目必须留注释的已知坑

这些是踩过的坑，改动相关代码时**保留**对应注释：

| 位置 | 坑 |
|---|---|
| Mapper XML 注释 | **XML 注释内不能出现连续两个以上 `-`**。写分隔线必须用 `====` 或 `====`+ 中文标题，**不能用 `----`**（否则 MyBatis 解析 XML 直接失败，应用启动崩溃） |
| `@Select("<script>")` | 按 XML 解析，`&lt;`/`&gt;` 必需。**不带** `<script>` 的走原始 SQL，此时写转义符反而语法错误 |
| Mapper 注册 | 同一 mapper id 不可同时存在注解与 XML 定义（MyBatis 取 XML、注解失效并打 ERROR） |
| `problem_tag` / `user_tag_rating` | 联合主键，故意不加 `@TableId`（Mapper 全仓只用 `selectList` 与自定义 SQL） |
| `docker/mysql-init/00-schema.sql` | Flyway 迁移不自足，空库基线必须由此文件建立（59 表 + 48 条迁移记录） |
| `SlidevPathProvider.findWorkspaceRoot()` | 找不到工作区根时兜底 `user.dir`，否则生产镜像启动即崩 |
| `courseware.url` | 其中的 uuid 目录名**不可改**，改名即断链 |
| `logback-spring.xml` | 两类 MyBatis-Plus 良性WARN 降到 ERROR（有意为之，不是掩盖问题） |
| Flyway 迁移文件 | 文件内注释一律不可改，改动会导致 checksum mismatch |

## 语言与格式

- **中文**为主，技术名词保留英文原文（`Redis`、`JWT`、`MyBatis-Plus`、`fail-open`）。
- 类头单行职责可写成 `/** 一句话职责。 */`，多行内容用完整 Javadoc 块。
- 行宽跟随 `.editorconfig`：Java 缩进 4 空格，前端 2 空格。
- Javadoc 中引用类型用 `{@link Xxx}`，不要裸写类名。

## 前端约定

- Vue 只给 `<script>` 块写注释，模板区不写 HTML 注释。
- composable 用Javadoc 风格块注释说明「返回什么、什么时候重新执行」。
- 组件注释说明**这个组件解决什么交互问题**，而不是复述模板结构。
- 复杂的 `watch` / 状态流转，在流转处写清「触发条件 → 副作用」。

## SQL 迁移约定

```sql
-- ============================================================
-- V52 拆分submission 表
-- 业务问题：原表把用户代码和判题元数据混在一起，查询单条提交需要
--           连带读取大字段 CODE，导致列表页查询性能随数据量线性劣化。
-- 处理：拆为 submission（元数据）与 submission_code（代码正文）两张表。
-- 前置依赖：V1 建立原始 submission 表。
-- 注意：拆分后需回填历史数据，见文末 INSERT ... SELECT。
-- ============================================================
```

三要素缺一不可：**业务问题、处理方式、前置依赖**。

> ⚠️ **默认规则：已经合入的迁移文件，一个字节都不要改。**
> Flyway 的 checksum 覆盖文件**全部字节**——注释、空行、行尾换行都算在内。
> 改动会让所有已建库的环境启动直接失败：`Migration checksum mismatch`，
> 而且重新执行迁移修不好，只能手工订正 `flyway_schema_history` 表。
> **需要补充说明时，优先写进 `docs/` 文档或代码注释，不要动迁移文件。**
> 这条规则曾在本项目被违反过一次（12 个迁移文件被改注释，导致起栈即崩）。
>
> 确实必须改时（例如注释里出现了本仓库不存在的引用），改动要**成对做**：
> 改文件的同时订正结构基线 `docker/mysql-init/00-schema.sql` 里记录的 checksum，
> 并同步已建库的 `flyway_schema_history`。完整步骤与校验方法见
> [数据库初始化目录说明](../docker/mysql-init/README.md#修改已合入的迁移文件)。

## Mapper XML 约定

```xml
<!--
  ================================================================
  按用户维度统计做题画像。
  ================================================================
  统计每个维度下的做题通过情况，供学情分析页展示。
  ================================================================
-->
<select id="selectProfileByTag" resultType="...">
```

三条硬性要求：

1. **注释内禁止出现连续两个以上的 `-`**。`--` 是 XML 注释的结束符，
   分隔线一律用 `====`。这一条写错会导致 MyBatis 解析失败、应用启动崩溃。
2. SQL 内的比较运算符仍需按 XML 规则转义（`&lt;`、`&gt;`、`&amp;&amp;`）。
   若本 Mapper 中有这类运算符，在注释里点明一句，提示后来者别「顺手修正」。
3. 不要为SQL 换行重排。MyBatis 的 `${}` 字符串拼接与条件标签对空白敏感，
   纯格式改动容易引发难以定位的行为差异。
4. 判断时间窗口的开闭性时，注意比较运算符在本项目里有多种写法：
   CDATA 形式 `<![CDATA[>=]]>` 与转义形式 `&gt;=` 混用。
   只统计其中一种会漏判，把「半开区间」错看成「闭区间」。
   判断前先通读该 select 的完整 WHERE 条件。
5. 更重要的是：**开闭性无法从参数名推断**。本仓库实测——
   `from/to` 一律半开 `[from, to)`（按时间段切片，相邻段不重不漏）；
   而 `startTime/endTime` 本身就有两种写法，既用于闭区间
   （作业提交：截止时刻前算交付），也用于半开（热力图：按天分桶，跨天不能重复计数）。
   改动这类 SQL 时，不要因为「别的查询用了另一种口径」就去统一。
